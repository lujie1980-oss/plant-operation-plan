第一部分 · 产品功能介绍

1. 产品定位

Plant Operation Plan 是一套面向单工厂的高级计划与排程（APS）系统， 将销售需求、物料齐套、粗能力平衡、主计划、详细排程、执行反馈与 KPI 串联为一条可运行的计划链路。 核心优化能力由 Timefold Solver 提供；日常排程交互以确定性推演为主，求解器为可选增强。

计划员

运行主计划、分析需求满足与产能、对比多场景策略

排程员

批次拆解、产线甘特排程、手动调整与推演确认

物料计划

齐套分析、物料需求滚算、缺料追溯

生产主管

产能负荷、工单下发、执行冲突监控

2. 典型业务场景

场景 A：从订单到主计划

销售订单进入需求池后，计划员需要回答：哪些订单能按时交付？瓶颈资源如何分配？不同策略（无限产能 vs 有限产能、延期最小化 vs 产能均衡）对结果有何影响？

  • 导入或维护销售订单 → 自动生成多级 BOM 工单
  • 运行齐套分析，过滤缺料订单
  • 选择主计划策略执行求解，得到资源×时间槽分配
  • 在需求满足、产能平衡、物料需求、生产工单等结果页切换计划场景对比

场景 B：从工单到产线排程

主计划完成后，生产排程以批次为最小排程单位。排程员在甘特图上拖拽、指定产线、全量/增量推演，确认后发布为排程版本与生产任务。

  • 已下发工单拆分为生产批次（固定批量 / 齐套拆批 / 手工）
  • 排程齐套按批次量消耗库存池
  • 创建 Scheduling Session，种子入队 + 链式赋时
  • 手动改序 → simulate → 查看违背 → confirm 落库

场景 C：计划变更与闭环

MES 反馈设备停机、缺料、加急等事件，系统按 R0–R3 级别决定是否重算主计划或详细排程；排程反馈可冻结 cutoff 前的工序计划时间。

场景 D：多数据集并行验证

通过 Workspace 隔离不同工厂/项目/演示数据集（如 default、te），切换后主数据、计划、排程完全独立，便于 POC 与回归测试。

3. 主计划设计

3.1 主计划策略（Master Plan Strategy）

「优化目标」页管理可命名、可复用的策略包，运行时在计划运行页选用。

字段说明
capacityStrategyUNCONSTRAINED 无限产能；FINITE_CAPACITY 按日产能拆段
objectives[]软目标：最小化延期、高优先级靠前、锁定订单靠前、相邻槽位产能均衡
isDefault未指定策略时使用默认

持久化于 system_parameter.param_id = 'master_plan_strategies'；每次求解写入 plan_version.strategy_id/name。

3.2 计划场景（Scenario）

一次主计划求解产生一个 planVersionId 场景。场景选择器（ScenarioSelector）通过 PlanContext 在四个分析结果页共享选中场景，切换后联动重载 API。

3.3 推演 vs 求解

阶段内容
P0 事实装载规划窗、TimeSlot、MRP 物料、BOM 边、最早可行下界
P1 工单筛选可排程、冻结窗、工艺非空、优先级
P2 工序展开product_resource → OrderAllocation；有限产能拆段
P3 可行域eligibleTimeSlots：资源匹配 + 反馈 overlay
P4 Timefold槽位分配 + 硬/软约束得分

3.4 满足链（Fulfillment Pegging）

满足链是供应追溯（非时间表）：销售订单 ← 成品库存 / 根工单 ← BOM 子件 ← 子工单 / 原材料库存 / 缺料。前端甘特仅展示业务节点与 peg 依赖边。

4. 生产排程设计

4.1 域边界

  • MRP 仍产出整张工单；批次仅在工单 dispatch_status = DISPATCHED 后创建
  • 已拆批工单：pending_schedule_eligible = false，仅 ACTIVE 批次进入 S05
  • S05 最小排程单位 = 批次（每批次独立占设备）

4.2 Scheduling Session 交互模型

POST create → 内存 Session（8h TTL）+ preview │ ├─ PATCH steps / POST simulate → 改队列 + 链式赋时 + 校验 │ ├─ [可选] POST optimize → Timefold 选优 + 赋时 │ └─ POST confirm → 持久化排程版本 + ProductionTask RELEASED

默认工作流：patch → simulate（不调用 Timefold）→ 查看 violations → confirm。Timefold 为可选增强。

4.3 批次拆解策略参数

参数说明
batch_split_modeNONE / FIXED_QTY / KITTING / AUTO
batch_fixed_qty固定拆批量
batch_remainder_modeFLOOR / CEIL / SEPARATE_TAIL / MERGE_TAIL
batch_kitting_create_short_batch齐套拆批时是否为剩余量建 SHORT 批次

4.4 业务规则与 SimulationProfile

业务规则页按 ruleTypeId 控制规则在主计划/详细排程是否启用。推演层另支持 SimulationProfile（config_json）与 simulate 请求级 ruleOverrides，二者与业务规则范围同时满足才启用规则。

ruleTypeId类型说明
changeover数据+Timing换型矩阵，赋时 cursor 间隙
operation-transfer-time数据+Timing+Closure工序衔接模式（同时开工/延迟/同时完工等）
parallel-operationsBinding+Validation并行工序对同线同起同止
continuous-productionBinding+Validation连续生产组队列内不得被其它料号隔开
factory-calendarTiming（Phase 3）开工 snap 到资源日历/班次窗口
feedback-freezeTiming+Validation（Phase 3）feedbackCutoff 前冻结反馈工序计划时间
batch-continuousClosure+Validation（Phase 3）同批次同线增量闭包；校验批次不被穿插

6. Workspace 多数据集设计

  • 一个 Workspace = 一套完整、互不可见的业务数据（约 20+ 业务表带 workspace_id）
  • HTTP Header X-Workspace-Id 传递；前端 localStorage.plantops.workspaceId 持久化
  • 唯一约束均为 (workspace_id, …) 组合；不同空间可用相同订单号/工单号
  • 新建 Workspace 时自动 ensureDefaults() 系统参数与业务规则默认行

2. S01 需求满足 — 实现逻辑

核心类

  • DemandService — 需求池加载、KPI 汇总
  • FulfillmentPeggingService — 满足链构建
  • WorkOrderGenerationService — 销售订单 → 多级 BOM 工单

满足链算法（pegDemand）

1. 创建销售订单节点 (depth=0)
2. 对需求量 product/qty：
   a. 扣减可用库存 → 创建 INVENTORY 节点 + INVENTORY_PEG 边
   b. 剩余需求 → 解析根工单（SO）或 parentWorkOrderNo 子工单（WO）
   c. 展开工单 BOM 关键子件，对每个子件递归 pegDemand
   d. 无法满足 → SHORTAGE 节点 + SHORTAGE_PEG 边
3. 内存维护库存扣减池，避免重复分配

API：GET /api/v1/demand/demand-pool、.../fulfillment-chain

3. S02/S03 齐套与产能 — 实现逻辑

S02 KittingService

  • 按 BOM 关键料与可用库存（扣减预留）逐单计算
  • 输出 KITTING_OK / SHORTAGE，持久化 kitting_result
  • S04 过滤不可排订单；S05 P2 按批次量消耗齐套池，设置 earliestStartMinute

S03 CapacityService

  • 按 resourceId × calendarDate × shift 聚合需求分钟与 resource_calendar.availableCapacityMinutes
  • analyzeForMasterPlan(versionId) 绑定选中主计划场景
  • 主计划负荷按工艺 CT（processTimeSeconds）计算工单工时，而非 runRatePerHour

4. S04 主计划 — 推演与求解

规划实体 OrderAllocation

一条记录 = 工单 × 工序 ×（可选）拆段。ID 格式：{workOrderNo}@OP{seq}_{ordinal}#{segmentIndex}

关键类链

MasterPlanPlanningContextBuilder.build()     // P0–P4
  → MasterPlanProblemMapper.toSchedule()       // Context → MasterPlanSchedule
  → MasterPlanService.solve()                  // Timefold
  → persist plan_version + master_plan_allocation

约束（MasterPlanConstraintProvider）

  • 硬约束：槽位容量（FINITE 模式）、资源匹配
  • 软约束：延期天数、优先级、锁定靠前、相邻槽位负荷均衡（权重来自 ResolvedStrategy）

物料 MRP（MaterialFeasibilityService）

P0 阶段预计算物料闭合库存与 BOM 依赖边，作为 Problem Fact 注入求解器；齐套损耗率叠加在 MRP 需求计算中。

5. 批次拆解 — 实现逻辑

SchedulingBatchResource / BatchSplitService

固定数量拆批：
  Q=工单量, B=批量, R=Q mod B
  FLOOR: floor(Q/B) 个整批
  CEIL: 最后不足 B 也成批
  SEPARATE_TAIL: 整批 + 尾批 R
  MERGE_TAIL: 最后一批 = B+R

齐套拆批：
  1. KittingService 计算 kittingEligibleQty
  2. 可齐套部分 → KITTED 批次
  3. 剩余 → SHORT 批次（参数控制）或留父工单

数量守恒：sum(ACTIVE batch.quantity) ≤ work_order.quantity。拆批后父工单 batch_split_status = SPLIT|PARTIAL，退出待排队列。

6. S05 Session 与链式赋时

DetailSchedulePlanningContextBuilder（P0–P4）

阶段实现
P0MasterPlanContractLoader — 工序窗口 + 目标资源软契约
P1ScheduleLine 列表，开线/产能
P2KittingService — kittingEligible、earliestStartMinute
P3DetailScheduleAssignmentBuilder — 批次→OperationAssignment
P4并行对、连续生产组绑定

产线队列模型（list-variable）

每条 ScheduleLine.assignedOperations 为有序 list；工序是否已排以 list 成员关系为准。Timefold 决策变量为产线/顺序；Session 路径通过 patch 改 list 后直接链式赋时。

DetailScheduleSessionMutation

SessionStepPatchDto:
  stepId      → operationId（必填）
  lineId      → 非空：移到该线并插入；空串：从所有线移除
  sequenceOnLine → 1-based 目标位置
  pinned      → 锁定标记

处理：pinned → 改线/改序（从全线移除再插入）→ 返回 touched stepIds 作为增量种子

DetailScheduleTimingKernel（链式赋时核心）

FOR iter = 1..16:
    applyLineQueuesOnce()           // 按产线 list 顺序扫 cursor 赋 start
    IF NOT bumpEarliestFromRoutingPredecessors(): BREAK

clampAssignedStartsToRoutingChain()
applyLineQueuesOnce()

单工序 start = max(
  cursor + changeover(前产品→今产品),
  earliestStartMinute,
  contractStartMinuteFloor,
  routingChainFloorStart
)

工艺链 OperationLinkMode:
  STANDARD         → predStart + predDuration + minGap
  SIMULTANEOUS_START → predStart
  DELAYED_START    → predStart + delayStart
  SIMULTANEOUS_END → predEnd - succDuration

LineChainTimingUtil.applyAllStartTimes 为静态门面，Timefold 求解后 DetailScheduleService.assignStartTimes 共用同一内核（Phase 4 对齐 Shadow 变量逻辑）。

7. 推演规则管道 — 实现逻辑

SimulationPipeline 阶段

Phase 1  ApplyMutations     DetailScheduleSessionMutation.applyPatches
Phase 2  ResolveMode        FULL | INCREMENTAL（闭包扩展 seeds）
Phase 3  ApplyTiming        DetailScheduleTimingKernel（TimingRule 插件链）

  2. 筛选 line!=null && startMinute!=null 的工序
  3. ProductionTaskService.releaseFromSchedule → RELEASED

     - 不一致 → planning_conflict (RUNNING_SCHEDULE_MISMATCH)
  4. sessionStore.remove(sessionId)
