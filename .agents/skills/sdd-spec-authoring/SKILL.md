# SDD 规范文档撰写指南

教你写出一份**好的规范文档**——它同时是业务蓝图、喂给 AI 的提示词、验收契约、回归测试的判据。

## 一条核心理念（先记住这个）

> 规范身兼三职：**给 AI 看的提示词** + **验收的契约** + **回归的测试预言**。
> 写规范时不断自问：「这句话，AI 据此能生成对的代码吗？测试能据此判定对错吗？业务和客户读得懂吗？」三个都点头，才算写好。

## 谁写哪部分

| 章节 | 主笔 | 必读 |
|---|---|---|
| 0 元信息 | 顾问 | 全员 |
| 1 价值与目标 | 产品 | 全员 |
| 2 统一术语表 ⭐ | 全员共建 | 全员 + AI |
| 3 角色与场景 ⭐ | 顾问 | 全员 + AI |
| 4 业务规则与约束 | 顾问 + 开发 | 开发 + AI |
| 5 领域模型与数据 | 开发 | 顾问可读 |
| 6 接口与集成契约 | 开发 | 开发 + AI |
| 7 标准化匹配与定制标注 ⭐ | 产品 | 全员 |
| 8 验收标准 | 全员 | 全员 + AI |
| 9 非功能要求 | 开发 | 产品 |
| 10 决策/假设/风险/待办 | 全员 | 全员 |

⭐ = 三面承重墙：**术语表**（消歧义）、**场景**（业务↔技术翻译层）、**标/非标标注**（产品可决策）。写不好这三块，整份规范就散了。

## 统一三视角的四个机制（写的时候务必遵守）

1. **统一语言优先**：动笔前先把术语表（§2）共建好。所有章节只能用表里的词，一词一义，禁用同义词。这是 AI 不乱编、各角色不打架的地基。
2. **以场景为中心**：用 `Given-When-Then` 写场景（§3）。同一场景：业务读是需求、开发读是契约、测试读是用例。业务和技术从此对齐。
3. **打标签让产品能决策**：每条能力标 `[STD]命中标准/[CFG]配置/[CUST]定制` + `[COMMON]通用/[SPECIFIC]特有` + `[REFLOW?]回流候选`（§7）。
4. **保持可追溯链**：`价值 → 场景 → 规则/实体 → 契约 → 验收 → 代码`，每条都带 ID、回指上游。改一环能追全链。

## 可追溯 ID 约定

`VAL`(价值) → `SCN`(场景) → `RULE`(规则)/`ENT`(实体) → `API`/`EVT`(契约) → `AC`(验收) → `NFR`(非功能) → `ADR`(决策)。蓝图标识 `BP-<客户>-v<N>`。每个条目用 `<前缀>-NN` 编号且回指上游 ID。

## 撰写流程（渐进精化 + 评审闸）

1. **售前**：写 §0/§1/§2/§3 粗版 → **蓝图评审**。
2. **合同后**：精化 §2~§6，补 §7 的 gap 分析 → **客户场景确认签字**。
3. **开发中**：细化非标逻辑（§4/§6）、补 §8/§9 → **技术契约评审**。
4. 别想一次写全。按阶段拉对应角色进来。

## 写好每一类内容的要点

### 场景（§3）—— 顾问重点
- 一个场景一个 `SCN`，挂在某个 `VAL` 下。
- `Given` 前置状态、`When` 触发动作、`Then` 可观察可验证的结果。
- **必须覆盖异常流**（产能不足、数据缺失、冲突）——异常流最容易漏，也最能体现专业度。

### 规则与约束（§4）—— 顾问+开发
- 分清 **硬约束（hard，绝不可违反）** 与 **软约束/目标（soft，优化方向）**。
- 硬约束写成"不变量"，它会变成属性测试，是质量护城河。
- 非标规则写到 AI 能据此生成代码的精度：输入、判定逻辑、输出。

### 价值与目标（§1）—— 产品
- KPI 必须可度量（baseline + target），将来要进运营指标跟踪。
- 写清"范围"与"非范围"，防蔓延。

### 标/非标标注（§7）—— 产品
- 对每条能力做 gap 分析并标三类标签。
- `[REFLOW?]` 的判定结论由产品经理在评审闸填（升 main / 留分支）。

### 验收（§8）—— 全员
- 每条 `AC` 可机械判定。
- ⚠️ **验收锚定规范（场景/规则），不锚定实现**——否则 AI 会把实现和测试一起写错还双绿。核心不变量验收必须人确认。

## 质量自检清单（提交评审前过一遍）

```
- [ ] 所有术语在 §2 已定义，无同义词混用
- [ ] 每个场景挂在某个 VAL 下，且含至少一个异常流
- [ ] 每条 hard 规则都有对应的不变量验收（§8）
- [ ] 每条能力都打了 STD/CFG/CUST 与 COMMON/SPECIFIC 标签
- [ ] 可追溯链完整：价值→场景→规则/实体→契约→验收
- [ ] KPI 与 NFR 可度量（有 target 与验证方式）
- [ ] 关键决策有 ADR，记录了 why 与备选
- [ ] 验收锚定规范而非实现
```

## 常见坑（避免）

- ❌ 写成一坨自由文本 Word：能结构化（术语/场景/标注/契约用 YAML 或表格）就结构化，否则没人维护、AI 难解析。
- ❌ 业务语言含糊到 AI 只能猜：非标逻辑要写到可生成代码。
- ❌ 只写正常流：异常流才是规范的价值所在。
- ❌ 客户特有需求塞进通用能力描述：明确标 `[SPECIFIC]`，别污染标准产品。
- ❌ 让 AI 同时写实现和测试还不审：测试要人对照规范把关。

## 规范治理三环（防止规范变废纸）

三类"看不见的偏离"会让规范慢慢死掉。解法是同一套思路：**把偏离变得可见且昂贵——用反馈环逼它自己跳出来**。

### 环一：防规范漂移 —— 让代码"不得不"从规范长出来
原则：不靠人同步规范与代码，让二者机器绑定，偏离即红灯。
- **能生成的别手写**：契约（§6）用 OpenAPI/事件 Schema 定义，接口骨架/DTO/事件类由它生成，代码只实现生成的接口。改接口必须先改规范。
- **契约测试入 CI**：Pact 验证实现没破坏已发布契约；ArchUnit 验证架构规则（分层、核心只读、通用模块不含业务）。破坏即红灯。
- **规范↔测试 ID 绑定**：测试打标注 `@SpecRef("AC-01")`；CI 校验每条 AC 至少被一个通过的测试引用、每个测试引用真实 AC（杜绝孤儿测试 / 没人测的 AC）。
- **PR 联动**：改契约代码却没动规范、或改 `sdd/` 却没动测试 → PR 标黄要求解释。"更新规范"写进 Definition of Done。
- **破坏性变更探测**：openapi-diff / pact 检出契约破坏 → 强制 ADR + 版本号 + 走评审闸。

### 环二：防过度规范 —— 用"换实现还成立吗"做试金石
原则：规范锁"什么对"（行为/契约/不变量），实现选择（算法/库/类结构）进 ADR。
- **试金石问句**（逐句问）：「换一种实现/换一个求解器，这句话还成立吗？」
  - ✅ 留规范："结果不得违反产能约束"（换任何求解器都成立）
  - ❌ 移出 → ADR："用 CP-SAT 建某布尔变量…"（这是 HOW）
- **what/how 结构分离**：行为/契约/不变量 → 规范（稳定）；技术/算法选型 → ADR（§10，显式标"可被推翻"）。
- **只测黑盒边界**：验收测试只调公开契约、看持久化结果与不变量，禁止断言私有方法/内部结构。
- **评审亮红**：规范里出现实现动词（"用 X 库""建一个 Y 类""循环遍历"）一律删或挪进 ADR。

### 环三：防隐性知识遗漏 —— 主动开采，让漏洞自暴露
原则：老师傅脑子里的东西不会自己进文档，要用机制逼出来。
- **异常流强制**：每个场景 ≥1 条异常流；AI 生成候选失败模式供专家勾选。
- **ADR 专记"为什么不选显而易见的那个"**：被否决的备选 + 原因最值钱，防 AI 重建时重踩坑。
- **从真实数据挖**：对客户数据做 profiling，把脏分布（空值/异常值/特殊标记）固化成边界用例 + 黄金数据集。
- **⭐ 重生成演练探漏**（定期）：让 AI 仅凭规范盲重建一个模块、跑闸；做得"似是而非"处 = 知识没沉淀的窟窿，回填规范/ADR/测试。这也是"规范写够好"的终极判据：**AI 仅凭规范重建的实现能过同一套闸**。
- **缺陷→规范棘轮**：每修一个生产缺陷，必须补一条场景 + 验收（必要时加 ADR）。让每个 bug 变成一条规范，窟窿单向填平、不回退。
- **当场入规范 + 回述确认**：专家讲解时当场写进规范并用业务语言回述请其确认。

> 投入重点不是"写更多规范"，而是"建这几个让偏离自己跳出来的环"。能被自动检验的偏离，才不会三个月后失控。

## AI 使用本 SKILL 时

- 加载后先读 §2 术语表，再据场景起草 §4/§6/§8 草案，并用业务语言回述请人确认。
- 主动巡检一致性（术语、场景挂价值、硬约束有不变量、标签完整、追溯链通），按"质量自检清单"反馈缺口。
